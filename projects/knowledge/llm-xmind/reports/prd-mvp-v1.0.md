# TraceMap｜证据驱动 AI 思维导图

> **产品需求文档（PRD） v1.0 · MVP 执行稿**  
> 项目归属：1998X / LLM × XMind · 文档状态：**待评审 / 未进入开发**  
> 文档日期：2026-11-09 · 负责人角色：Product Owner（待指定） · 适用范围：Web MVP  
> 工作代号：TraceMap（暂定，不代表商标或域名已注册）

**一句话定位**：让需要阅读多份资料、提出判断的研究者，在一张可编辑、可追溯的思维导图中完成“理解—核验—修正—交付”，而不只获得一次性 AI 摘要。

**版本决策**：先验证“节点级证据 + 局部 AI Patch + Xmind 可用导出”是否显著优于常规 AI 摘要/脑图；不做通用白板，不做全自动研究 Agent，不替代 Xmind 的完整绘图能力。

### 0.1 产品决策依据与证据强度

- **外部已核实**：Xmind 已有 Agent / MCP 路径，且官方支持导入 Markdown 为思维导图。这说明“能生成导图”“能用 AI 改导图”已难形成单独差异化；Markdown 可作为首版 Xmind 兼容导出通道。[S1][S2][S3]
- **研究归纳**：先前 HN / Product Hunt 研究指出，资料核验、分支控制、局部修改和持续工作流是值得测试的方向；这是定性洞察，不是用户规模、留存或付费事实。[R1]
- **待验证假设 H1**：用户会为“事实可核验、误改可回滚”付出比纯视觉美化更高的持续使用成本。
- **待验证假设 H2**：在 30–60 分钟的多文档研究任务中，证据导航与局部改图能使完成时间减少 ≥25%，且不降低事实准确性。
- **待验证假设 H3**：导出 Markdown 并转入 Xmind 足以满足首批用户的继续编辑需求；不必在 MVP 开发原生 .xmind 导出。

### 0.2 明确的竞争定位

| 方案 | 交付物 | TraceMap 要赢的具体任务 |
| --- | --- | --- |
| ChatGPT / Claude + 人工整理 | 文本对话、摘要、人工搬运 | 从关键观点一键跳回原文，局部修正而非重生成整篇 |
| Xmind 2027 / 传统导图工具 | 高成熟度画布、AI Agent、导图编辑 | 更严格的证据节点与冲突显示；**不宣称整体体验胜出** |
| 一键 PDF→脑图产品 | 从材料到可视结构的速度 | 对关键结论的可核验性、可修改性和隔日接续 |

## 01｜问题、用户与关键场景

### 1.1 核心问题（Problem Statement）

研究者面对多来源内容时，LLM 很快给出一棵看似完整的树，但树上的结论可能丢失原文语境、合并相互矛盾的说法；一旦用户改变某个节点，又可能不得不重复生成整张图，或无法知道哪些内容被偷偷修改。最终，导图成为展示品而非可以持续用于决策的工作资产。

### 1.2 首要 Persona / JTBD

**P1 · 独立产品研究员（主用户）**：每周至少进行 1 次竞品、用户反馈或新赛道研究；会使用 LLM、笔记软件和至少一种导图工具；对“能给团队解释依据”有强需求。**JTBD**：当我收到相互重叠且局部矛盾的资料，希望迅速组织结论并保留来源，以便在评审时解释“为什么这样判断”。

**P2 · 学生/知识工作者（次用户）**：需要读长文、课程资料并识别不懂的点；可能重视学习成效，但首版不以学习评分和复习系统为目标。

**明确排除首轮用户**：需要法律/医疗合规保证的专业决策团队；要求多人实时协同的团队；只想生成漂亮汇报海报、不愿核验来源的人群。

### 1.3 最核心的三个使用场景

| 场景 | 触发 | 完成定义 |
| --- | --- | --- |
| UC-01 多文档竞品研究 | 用户上传 3 份产品资料，想整理定位、优势、问题 | 产生约 15–40 个节点；全部标记关键主张的证据状态；能导出可继续编辑的结构 |
| UC-02 发现来源冲突 | 两份材料对同一功能描述不同 | 用户能同时打开两处原文、在图中保留反例/待确认，不把冲突合成为“确定事实” |
| UC-03 评审后的局部修订 | 评审要求补充“定价/竞争风险” | 只生成目标分支的 Patch 预览；确认后改动局部；撤销可以恢复原样 |

### 1.4 从“输入”到“可交付成果”的黄金路径

1. 新建项目，粘贴文本或上传含可复制文本的 PDF / Markdown（最多 5 个来源）。
2. 系统展示提取预览、文件名与解析失败项；用户明确选择“生成研究地图”。
3. AI 在预设 Schema 下生成地图草稿；画布呈现主题树，侧栏为来源列表。
4. 用户点击一个“主张”节点，在证据面板看到引用片段和原文上下文；不确定项标记为“待验证”。
5. 用户对一个节点选择“展开 / 精简 / 挑战观点 / 提取问题”，查看操作前后 Diff，只确认需要的部分。
6. 用户把关键节点标为“已核验”或“待确认”，保存研究状态并能隔日重开。
7. 导出层级 Markdown，在 Xmind 中导入继续排版；同时可导出 JSON 作为完整证据结构的备份。

## 02｜MVP 边界与优先级

### 2.1 必做 P0 / 应做 P1 / 不做 P2

| Epic | 核心能力 | P0（首版必须交付） | P1（验证后再加） | 明确不做（本轮） |
| --- | --- | --- | --- | --- |
| E1 | 项目与资料 | 项目 CRUD；粘贴文本、.md、可提取文本 PDF；解析预览 | URL 输入、更多文件类型 | 自动跨站爬取、OCR、多租户资料库 |
| E2 | 证据导图生成 | 稳定 JSON Schema、有限节点树、结论来源标签 | 结构模板、自动冲突候选 | 无限层级自动研究、自动改写来源 |
| E3 | 画布交互 | 展开折叠、选中、重命名、新增/删除/移动、撤销 | 多选、快捷键大全、跨图连接 | 通用白板、多人实时光标 |
| E4 | 节点证据 | 原文引用、来源跳转、已核验/待验证状态 | 相似引文匹配、批量标注 | 模型“自证正确”、自动外部事实查证 |
| E5 | AI 局部 Patch | 展开、精简、质疑、生成问题；diff→确认→撤销 | 分支比较/合并、提示词自定义 | 自主修改全图、后台 Agent 循环 |
| E6 | 保存与版本 | 自动保存、版本节点、操作日志、单步撤销 | 时间线回溯与快照对比 | Git 式多人分支协作 |
| E7 | 导出与兼容 | 层级 Markdown、结构化 JSON、导出前预览 | PNG/SVG、原生 .xmind（需技术评估） | PPT 模板、企业项目管理联动 |

**版本约束**：所有 P0 构成完整可用链路；如果时间/资源不足，应优先砍 P1，而不是砍来源核验、Patch 审阅或保存恢复能力。

### 2.2 明确非功能边界

- 首版仅支持简体中文、英文输入及输出；不承诺多语混合材料的无损翻译。
- 每项目最多 5 个来源，每个文件 ≤10 MB；提取的总正文 ≤80,000 字符，超过时明确提示用户缩减，而不是静默截断。
- PDF 必须有可提取文本层；扫描件明确提示“不支持 OCR”，不产生伪解析结果。
- 首版采用单用户项目隔离；需要登录以跨设备保存；不做团队空间、角色权限体系。
- 不承诺模型生成内容都正确，不给未经核实的结论贴“可信事实”标签。

## 03｜P0 核心功能详细规格

### E1｜项目管理与资料导入

**用户故事**：作为研究员，我希望导入少量可信资料，并在生成前检查提取结果，以免把缺页/乱码当作模型的理解错误。

| ID / 优先级 | 交互与业务规则 | 验收标准（Given / When / Then） |
| --- | --- | --- |
| FR-101 / P0 | 项目创建：名称（1–80 字符）、描述可选；记录 owner、时间；项目列表按最近修改排序 | Given 已登录，When 新建项目并刷新，Then 项目仍存在且仅本人可读写 |
| FR-102 / P0 | 输入支持粘贴正文、UTF-8 Markdown、可复制文本 PDF；每个来源显示标题、类型、字数、解析状态 | Given 合规文件，When 上传完成，Then 可见提取预览且保存 Source ID；不能读取的文件不进入生成队列 |
| FR-103 / P0 | 配额：5 来源、单文件 10 MB、合计 80k 提取字符；前后端双重限制 | Given 超额/空文件/扫描 PDF，When 导入，Then 返回具体错误与补救方案，无静默裁剪 |
| FR-104 / P0 | 每个来源生成稳定段落 ID、原文位置、哈希，保存用于引用定位 | Given 一份被提取的文档，When 点击来自它的证据，Then 能定位对应段落，显示文件名及上下文 |
| FR-105 / P0 | 删除来源时提示“多少节点引用该来源”，并将关联节点转为待验证 | Given 有关联证据，When 删除来源并确认，Then 不留下虚假的“已核验”状态 |

**界面状态**：空态（样例资料）、解析中（可取消）、解析成功（文本预览）、部分成功（逐文件失败原因）、拒绝（大小/格式/无文本）、源文件删除确认。**安全规则**：上传内容不作为系统指令；禁止文档中的 prompt injection 覆盖产品约束。

### E2｜结构化生成与导图语义

**用户故事**：我希望模型产生可以修订的研究结构，而不是随机排版的漂亮句子，并知道每个关键判断来自哪里。

**节点类型**：`topic`（主题）、`claim`（主张）、`evidence`（支持依据）、`counterpoint`（反例/冲突）、`question`（待确认问题）、`decision`（用户结论）。`topic` 只组织结构；`claim` 必须有证据或“未核验”提示；AI 不可擅自把节点设为“已核验”。

| ID / 优先级 | 交互与业务规则 | 验收标准 |
| --- | --- | --- |
| FR-201 / P0 | 生成任务由用户显式触发；输入项目选定来源、研究目标、输出语言 | 有效资料与目标 → 生成结构化树；无有效资料 → 阻止调用并说明原因 |
| FR-202 / P0 | 服务端校验模型 JSON：唯一 ID、合法 type、单根树、无环、最大 5 层、最多 120 节点 | 非法 JSON 自动尝试受限修复一次；仍失败返回“生成失败”，不得存半成品 |
| FR-203 / P0 | 每个 AI `claim` 携带 `evidenceRefs[]`，引用须指向项目内真实 source/paragraph；找不到则 `unverified` | 伪造 ID/不存在的引文不能显示成有效来源；校验失败时标记“未核验” |
| FR-204 / P0 | 原文对不一致/不确定内容，不生成确定性合并；可使用 `counterpoint` / `question` | 测试材料中预置冲突，在人工评测中检查是否保留双方说法；算法不承诺 100% 找全 |
| FR-205 / P0 | 生成前保留 source hash + 模型版本 + Prompt 版本；每次输出成为可恢复快照 | 刷新页面后可看到原图、生成记录和版本信息；不存储无必要的原始密钥 |

**生成策略**：资料按段落切分，使用确定性 schema 输出；仅在用户已导入的材料范围内总结，不默认调用互联网。引用生成后在服务端验证 `sourceId + paragraphId + snippet` 是否可追溯；对仅“语义相似”而无法文本定位者标记待核验。**优先保真而非补齐**，空白由问题节点表达。

### E3｜导图画布与手工编辑

**用户故事**：我希望能像使用成熟导图工具一样直接修改结构，并保留自己对知识的判断。

| ID / 优先级 | 交互与业务规则 | 验收标准 |
| --- | --- | --- |
| FR-301 / P0 | 画布支持节点选中、展开折叠、缩放和适配视图；右侧显示节点详情 | ≥120 节点测试图可正常展开、定位，基本编辑无明显卡顿；测量帧率而非宣称保证 |
| FR-302 / P0 | 双击修改标题；添加子节点/兄弟节点；删除节点需确认其子树影响 | 修改后 2 秒内可见“已保存/保存中”；刷新不丢失已确认操作 |
| FR-303 / P0 | 拖拽/菜单移动节点可调整父子关系和同级顺序；禁止移到自身后代 | Given 子树 A，When 移到其后代 B，Then 操作被拒绝且树不被损坏 |
| FR-304 / P0 | AI 生成节点与用户手工节点视觉可区分；“已核验”仅由用户主动设置 | Given 手工结论，When 保存，Then 不被后续 AI 局部操作覆盖（未确认前） |
| FR-305 / P0 | 撤销最近一次已提交的结构化变更，恢复节点与证据状态 | 连续执行“增加→移动→删除”，逐步撤销后结构与变更前等价 |

**布局原则**：以层级阅读效率优先；AI 修改后尽可能保留未修改分支的位置、缩放和折叠状态。MVP 不承诺高级自由布局和复杂关系图。

### E4｜引用、证据核验与冲突提示

**用户故事**：我在评审会上必须解释“这一点到底从哪里来”，并能区分“来源说了什么”和“我的判断是什么”。

| ID / 优先级 | 交互与业务规则 | 验收标准 |
| --- | --- | --- |
| FR-401 / P0 | 点击节点的“引用标签”打开证据侧栏：来源名、段落、引用文字、前后文 | Given 合法引用，When 点击标签，Then 可看到对应原文段落（不是 AI 重新转述） |
| FR-402 / P0 | 引用标签状态：可定位 / 待核验 / 来源已删除 / 引用失效；颜色之外还有文字与图标 | Given 引用段落不存在，When 展示节点，Then 不出现可点击的伪造原文链接 |
| FR-403 / P0 | 用户可为 `claim` 标记“已核验”，可随时撤销；核验动作有时间与操作者记录 | Given 未核验的主张，When 手工核对并确认，Then 状态变化且审计日志可查 |
| FR-404 / P0 | 在证据侧栏可将来源片段添加为 `evidence` 或 `counterpoint`，避免重写原文 | Given 两处矛盾片段，When 分别添加，Then 保留两条不同证据与其来源 |
| FR-405 / P0 | 导出报告标注关键主张的核验状态；Markdown 展示简短来源脚注 | Given 有待核验主张，When 导出，Then 不会误标为“已证实” |

**不可逾越边界**：本产品提供“出处可追溯”，不等于内容本身真实；来自用户上传来源的错误信息也可能被准确引用。严禁把“有引用”等同“真实性已确认”。

### E5｜AI 节点级 Patch（主要差异化）

**用户故事**：我希望在一个特定节点上让 AI 补充论证或反例，却不重新生成全部导图、不丢弃我的修改。

**四个首版操作**：① `expand`：补充已上传来源中相关子论点；② `condense`：压缩选中子树；③ `challenge`：从来源中提出反例/证据缺口；④ `questions`：生成下一轮人工核验问题。

| ID / 优先级 | 交互与业务规则 | 验收标准 |
| --- | --- | --- |
| FR-501 / P0 | 只选择一个目标节点/子树；请求附带 targetNodeId、baseRevision、source scope、operation | Given 选中节点 A，When 执行 expand，Then Patch 不含 A 之外的写操作 |
| FR-502 / P0 | 模型只返回操作集合（add/update/delete/move），服务端应用白名单校验 | 非法路径、无权项目、循环父子关系、越界节点均拒绝，无状态变更 |
| FR-503 / P0 | 修改前显示 Diff：新增绿色、删除红色、替换前后文，证据变更单列展示 | Given 3 个候选操作，When 打开预览，Then 用户能逐项接受/拒绝，默认**不自动应用** |
| FR-504 / P0 | 乐观并发：预览期间如果目标子树 revision 变化，旧 Patch 失效并提示重新生成 | Given baseRevision=4、当前 revision=5，When 提交旧 Patch，Then 返回冲突并保持当前地图 |
| FR-505 / P0 | 确认应用后创建 changeSet/快照；提供撤销，保留来自用户的手工已核验状态 | Given 接受 Patch，When 撤销，Then 原子恢复；没有未经确认的修改留存 |
| FR-506 / P0 | 失败时保留原图、显示可重试错误；记录模型耗时与 token/成本元数据 | 超时/模型输出异常时，地图完全不受影响，并提示“没有应用任何修改” |

**操作顺序**：选节点 → 选操作 → 可选补充目的 → AI 生成建议 → Diff 审阅 → 用户逐项勾选 → 服务端再次校验 → 原子写入 → 更新版本与审计。**MVP 严禁模型直接持久化地图**。

### E6｜保存、恢复与最小版本机制

| ID / 优先级 | 交互与业务规则 | 验收标准 |
| --- | --- | --- |
| FR-601 / P0 | 用户操作为服务端原子事务，返回 revision；编辑状态显示保存中、已保存、失败 | 模拟断网/刷新后，不出现客户端声称成功但服务器没有提交的操作 |
| FR-602 / P0 | 记录每个确认操作的 actor、动作类型、前后差异与时间；保存最近 20 次变更 | Given 20 次以内变更，When 选择撤销，Then 恢复对应结构及引用状态 |
| FR-603 / P0 | 项目列表“最近访问/继续研究”；重新打开恢复最新已确认版本与折叠状态 | 隔日（或模拟新会话）重开，原资料和已核验状态可继续编辑 |
| FR-604 / P0 | 用户可删除项目及全部关联资料；删除行为确认且不可恢复 | 删除后，用户列表与应用查询均不能再获取项目；备份清除周期需在上线前公开 |

### E7｜导出与 Xmind 兼容

| ID / 优先级 | 交互与业务规则 | 验收标准 |
| --- | --- | --- |
| FR-701 / P0 | 导出层级 Markdown：标题映射节点层级，使用 `#`–`######`，超过 6 层按限制处理 | Given 5 层合法图，When 导出 .md，Then标题层级稳定、UTF-8 正常、可被 Xmind Markdown 导入路径识别 |
| FR-702 / P0 | 导出结构化 JSON：节点 ID/type、关系、source refs、verification、版本号 | 导出后重新校验 JSON Schema，数据完整，可供未来迁移（暂不承诺回导 UI） |
| FR-703 / P0 | Markdown 导出保留来源脚注/原文索引，但说明 Xmind 不一定完整还原证据侧栏 | Given 证据标注，When 导出，Then .md 仍可阅读引用信息；不会承诺“无损转移” |
| FR-704 / P0 | 在正式发布前以官方 Xmind 桌面或 Web 导入实测覆盖中文、英文、深层级、特殊字符 | 测试矩阵全部通过才标记“已验证兼容”；失败则在 UI 降级为“导出 Markdown” |

**兼容策略**：不逆向实现 `.xmind` 格式。用 Xmind 官方已公开支持的 Markdown 导入建立可靠互通；真实格式保真度必须以端到端导入测试为准。[S1]

## 04｜核心页面与信息架构

### 4.1 页面 IA

| 页面 | 主要区域 | 主要行动 | 空态/错误态 |
| --- | --- | --- | --- |
| `/projects` 项目列表 | 项目卡片、最近更新、状态 | 创建、打开、删除 | 首次使用引导示例项目 |
| `/projects/:id/sources` 资料页 | 文件列表、提取预览、研究目标 | 上传、粘贴、删除、生成 | 文件解析失败/超额/无可用文字 |
| `/projects/:id/map` 地图页 | 左来源、中央画布、右节点/证据/AI | 编辑、核验、Patch、导出 | 生成失败、空地图、证据失效 |
| `/projects/:id/history` 最小历史 | 操作记录、时间、撤销 | 恢复上次已确认更改 | 没有历史时提示 |
| `/settings/privacy` 隐私页 | 模型处理说明、项目删除 | 删除数据、读取说明 | 没有未授权隐式访问 |

### 4.2 低保真交互布局

```text
┌ 项目 / 资料 / 导图 / 导出                        保存状态 ┐
│ 左侧：资料来源      │ 中央：研究地图        │ 右侧：核验 / AI  │
│ □ Source A          │ 主题                  │ 节点：某项结论   │
│ □ Source B          │  ├─ 主张 A  [2]       │ 来源引用 [定位]  │
│ □ Source C          │  │   └─ 证据           │ 状态：待核验     │
│ 搜索来源            │  ├─ 反例 B [1]        │ [确认已核验]     │
│ 文段预览            │  └─ 问题 C [?]        │ [展开][提出反例] │
│                     │                        │ Patch Diff 预览  │
└────────────────────────────────────────────────────────┘
```

**设计原则**：左边显示“材料”，中间显示“结构”，右边显示“证据与操作”，让用户始终知道自己在改变什么。对来源无法验证的节点使用文字、图标与浅色状态并存，不只靠颜色；所有 AI 自动变更必须有明确的用户确认动作。

### 4.3 关键状态机

- Source：`queued → parsing → ready | failed → deleted`。
- Map generation：`idle → generating → draft | failed`；只有 `draft` 可由用户确认成正式版本。
- Patch：`requested → proposed → accepted/rejected | expired`；`proposed` 状态只读，不得影响正式地图。
- Verification：`unverified → verified_by_user → unverified`；来源失效强制回到 `unverified`。
- Save：`dirty → saving → saved | error`；出现 `error` 时不呈现成功状态。

## 05｜关键数据模型与技术边界（供工程评审）

### 5.1 最小领域模型

| 实体 | 最小字段 | 不变量 |
| --- | --- | --- |
| Project | id, ownerId, title, goal, revision, timestamps | 每次写入校验 ownerId |
| Source | id, projectId, title, kind, sha256, status, extractedCharCount | 可唯一定位原始上传物与解析版本 |
| Paragraph | id, sourceId, text, pageNo?, offsetStart?, offsetEnd? | `sourceId + id` 不随生成而变化 |
| Node | id, projectId, parentId, sortKey, type, title, note, origin, verification | 单根树、无环；人标记的核验不能被 AI 自动升级 |
| EvidenceRef | id, nodeId, sourceId, paragraphId, exactQuote, validity | 只引用本项目真实段落；来源失效需降级 |
| Patch | id, targetNodeId, baseRevision, ops[], status, modelInfo | 只有 validated & accepted 才能应用 |
| ChangeSet | id, projectId, revisionBefore/After, actor, inverseOps, timestamp | 原子提交、可回滚和审计 |

### 5.2 服务契约（说明级草案，非已上线 API）

```http
POST   /api/projects                    创建项目
POST   /api/projects/:id/sources        上传/粘贴来源
POST   /api/projects/:id/generate       创建生成任务
GET    /api/projects/:id/map            读取导图与 revision
POST   /api/projects/:id/nodes/ops      执行手工原子操作
POST   /api/projects/:id/patches        请求 AI Patch（仅预览）
POST   /api/projects/:id/patches/:pid/apply  确认选定操作并应用
POST   /api/projects/:id/undo           撤销最近确认操作
GET    /api/projects/:id/export?format=md|json
DELETE /api/projects/:id                彻底删除项目（按公开策略）
```

关键返回约定：每次写操作携带 `If-Match: projectRevision` 或等效字段；不匹配返回 `409`，无权返回 `403/404`，不支持资料格式返回 `415`，配额超限返回 `413/422`，模型异常返回具有可重试标识的 `5xx`；接口不能向前端暴露模型密钥。

### 5.3 AI I/O 结构化示例

```json
{
  "targetNodeId": "n_claim_12",
  "baseRevision": 7,
  "operation": "challenge",
  "proposedOps": [
    {
      "op": "add",
      "parentId": "n_claim_12",
      "node": {
        "type": "counterpoint",
        "title": "另一来源存在不同描述",
        "evidenceRefs": [
          {"sourceId": "src_b", "paragraphId": "p_21", "exactQuote": "原文片段"}
        ],
        "verification": "unverified"
      }
    }
  ]
}
```

服务端**必须**检查：项目权限、目标节点范围、引用实体存在、原文引用吻合、操作合法性、revision 新鲜度、用户选择项；再提交数据库事务。模型只提议，不获直接写库权限。

### 5.4 非功能需求与安全

| 类别 | 可验收目标 / 处理原则 |
| --- | --- |
| 性能 | 50 节点图在主流桌面 Chrome 的普通笔记本上可交互；**测试目标**：p95 首屏 ≤3 秒（不含模型生成），手工节点操作反馈 ≤300ms。上线前实测 |
| AI 时延 | 数据提取与生成异步反馈；生成超 60 秒仍未完成，显示进度/可取消；上限和真实 p95 由封闭测试校准 |
| 可靠性 | AI/网络失败不得破坏最近一次已保存地图；Patch 原子事务与 undo 回归测试全通过 |
| 安全 | 端到端 TLS；服务端权限校验；上传格式白名单；文档文本隔离为“不可信输入”；防越权引用 ID |
| 隐私 | 明示外部模型提供商、数据用途与留存策略；不得未经核实宣称“数据不会用于训练”；默认不公开分享用户资料 |
| 可访问性 | 不只靠颜色表达证据状态；核心功能具备键盘焦点与文本标签；按 WCAG 2.2 AA 做抽样审查 |
| 可观测性 | 记录任务状态、错误码、耗时、token/成本区间；默认不把资料正文写入应用日志或分析事件 |
| 数据治理 | 项目删除后在线数据库与对象存储应按文档化策略处理，备份保留/删除周期上线前经技术与法务确认 |

## 06｜埋点、质量验证与 Go / No-Go

### 6.1 事件字典（不上传原文正文）

| 事件名 | 何时触发 | 关键字段 |
| --- | --- | --- |
| `project_created` | 创建成功 | projectId, cohort |
| `source_parsed` | 每个来源解析结束 | kind, charBucket, success, failureReason |
| `map_generated` | 用户确认导图草稿后 | durationMs, nodeCount, unverifiedCount, modelVersion |
| `citation_opened` | 用户打开来源证据 | nodeType, citationValidity |
| `claim_verified` | 用户确认结论已核对 | sourceCountForClaim, nodeType |
| `patch_previewed` | 展示 Diff | operation, opCount, latencyMs |
| `patch_applied` | 用户确认应用 | acceptedOps, rejectedOps, conflictFlag |
| `undo_performed` | 撤销成功 | changeSetType |
| `map_exported` | 导出成功 | format, nodeCount |
| `project_reopened` | 同一项目新会话进入 | daysSinceLastEdit |

### 6.2 核心指标与门槛（均为目标值，不是现有成绩）

| 指标 | 测量方式 | Go 条件 / 红线 |
| --- | --- | --- |
| 关键结论可追溯率 | 抽样人工审计：可指回正确原文的关键主张 / 被抽样主张 | ≥90%；**伪造来源 ID = 0** |
| 关键事实覆盖率 | 专家预标注关键事实，复核导图覆盖 | ≥85% |
| 冲突发现召回率 | 预置冲突对，核对是否保留对立信息 | ≥80%；失败原因必须可分析 |
| 有效完成率 | 受试者独立从导入到输出形成可审核结论 | ≥70% |
| 任务用时 | 与 ChatGPT/Claude + 人工整理交叉对照 | 目标改善 ≥25%，同时事实质量不降低 |
| 修改可控性 | Patch 越界/误改、撤销失败回归 | 重大不可恢复误改 = 0 |
| 持续使用信号 | 7 天内回到同一研究项目的用户比例 | 先收集基线；**不预设伪精确阈值** |
| 付费信号 | 招募测试者中明确愿意以真实预算试用/采购的比例 | 作为探索指标，不据此宣称 PMF |

### 6.3 研究设计

招募 **12–18 位**目标用户，进行同一任务集的交叉实验：A 常规 LLM + 手工整理；B 现有 AI 导图；C TraceMap 原型。每份任务含 2–5 个来源和 1–3 处预置矛盾。顺序平衡、统一材料与时间窗，评分者尽量盲审。记录任务完成、事实错误、漏项、来源定位时长、局部修改次数与用户自主感；两次任务间隔一天，检查接续能力。

**Go**：准确性红线通过，主用户在多文档研究任务中至少呈现一个显著、可复现的效率或质量优势，且愿意继续使用。**Iterate**：质量过关但效率不占优，优先优化引用定位/交互。**No-Go / Pivot**：无法可靠关联来源或 Patch 不可控，暂停扩展范围，不靠增加 AI 功能掩盖问题。
