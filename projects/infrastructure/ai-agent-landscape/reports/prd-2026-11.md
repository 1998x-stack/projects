> **Working title / 暂定名称：** EvidenceFlow Agent  
> **Document ID：** EF-PRD-001 · **Version：** 1.0 · **Date：** 2026-11-09  
> **Document status：** 产品方案草案 / 待用户验证，**不是已交付产品**  
> **Owner：** 1998X Projects（产品研究） · **Target：** 0→1 MVP / Web SaaS  
> **Related：** [AI-Agent 市场研究](./research-2026-11.md) · [MVP 详细功能规格](./mvp-functional-spec-2026-11.md)

## 0. Executive decision / 一页产品决策

| 问题 | 决策 |
| --- | --- |
| 做什么 | 面向 AI/SaaS 创业者与产品经理的 **“带证据的竞品调研 Agent”**：自动组织有限来源、抽取竞品事实、生成对比报告，要求人类在发布前确认 |
| 核心用户 | 1–30 人 AI/SaaS 团队的创始人、PM、产品策略/增长研究人员 |
| 首个任务 | 给定 3–5 个竞品与 3 个研究问题，在受控来源范围内生成可回溯证据的产品对比简报 |
| 核心价值 | **减少验证与返工的总时间**，而不仅是加快“写出第一稿” |
| 优先不做 | 通用电脑操作、邮箱/CRM 写入、自动发帖、实时全网监控、多 Agent 自治、复杂权限平台 |
| 唯一主指标 | 经用户接受的、证据达标的研究报告数 / 周（Accepted Evidence-backed Reports，AER） |
| Go / No-Go | 先进行人工基线对照实验；仅当质量、核验耗时和单位成本达门槛，才扩大到 Beta |

**一句话定位：** “研究报告不仅给出结论，还能准确指出每条关键结论从哪里来、何时获取、哪些仍待确认。”

**产品原则：** Human owns judgment; the agent owns the repeatable process. / 人类保留判断权，Agent 负责可审计的重复流程。

## 1. 背景、问题与证据

### 1.1 研究输入：已观察到什么

本项目此前分析了 Manus、ChatGPT Work、Genspark、Perplexity、Claude Code、Cursor、Devin、OpenClaw、n8n、Zapier Agents 等共 14 个代表性产品/产品线。研究指出：通用 Agent 的体验通常取决于工作环境、人工接管和结果核验，而不只是模型能力；HN 讨论更集中于可信度、修复成本与授权风险，PH 评价更多体现首次体验和功能展示。[研究全文](./research-2026-11.md)

研究还引用了 METR 2025 年针对特定开发者任务的随机对照实验，以及 2026 年存在选择偏差的更新；这些研究**不能**直接证明研究类 Agent 的 ROI，却说明“生成速度”不能替代“完成人工审查后的总时间”指标。参考：[METR 论文](https://arxiv.org/abs/2507.09089)、[后续更新](https://metr.org/blog/2026-02-24-uplift-update/)。

### 1.2 尚未验证的用户痛点（HYP）

1. 初创团队需要经常比较竞品定位、功能、价格与用户批评，但搜集原始资料与清洗重复观点花费大量时间。
2. 现有 AI 调研输出有时措辞笃定但来源无法支撑结论，用户必须逐条回查。
3. 关键变化（例如定价、产品形态）有时被写成永久事实，没有采集日期与状态。
4. 现有“会搜索的聊天窗口”很难沉淀可复用的竞品证据库和版本化交付物。

以上属于**产品假设**，来源为竞品评论的归纳与专业推断，尚未通过目标用户访谈证明；不得作为市场规模、PMF 或客观效率数据对外宣传。

### 1.3 设计推论：为什么先做这个窄切口

与高度开放的浏览器/电脑 Agent 不同，竞品研究工作可限定数据源、事实类型、输出结构和审批环节；大部分动作是**只读**，安全边界更清晰；交付质量可通过人工抽样与来源核对衡量。选择这一场景是为了获得可度量的真实成功率，而非断言它必然是最大市场。

## 2. 目标用户、JTBD、使用场景

### 2.1 首发 ICP（P0）

- **角色：** B2B AI/SaaS 创始人、0→1 PM、小团队产品策略研究人员。
- **场景：** 做立项、竞品 review、定位调整、月度策略会议前，需要一份准确、可分享、能解释出处的对比报告。
- **现有替代：** 浏览器标签 + HN/PH 搜索 + 官方网站 + 表格/Notion + ChatGPT 手工整理。
- **非目标用户：** 投行级尽调、法律或医疗专业结论、需要数百站点监测的大企业、要求 Agent 替用户执行外部不可逆操作的团队。

### 2.2 JTBD

“当我需要判断一个 AI/SaaS 方向能否切入时，我希望在限定的可信来源内完成 3–5 家竞品的定位与用户反馈对比，并能点击每条重要结论去看原始证据，从而快速形成可讨论、可修改的决策备忘录。”

### 2.3 三个首发使用场景

| ID | 使用场景 | 触发输入 | 合格输出 |
| --- | --- | --- | --- |
| UC-01 | 新赛道竞品扫描（主路径） | 主题、3–5 家竞品、3 个研究问题 | 竞品矩阵 + 来源注释 + 机会假设 + 未证实清单 |
| UC-02 | 定位与价格核实 | 用户给出的官方网站/定价页 | 标注获取日期的定位/价格字段；找不到则“待确认” |
| UC-03 | 社区反馈提炼 | HN 公开讨论链接/受支持搜索结果；用户主动提供的 PH 笔记 | 区分正/负反馈、观点所属人群和样本局限的摘要 |

**P0 只为 UC-01 完成完整端到端闭环；UC-02/03 是复用同一来源与证据能力的变体。**

## 3. 产品范围与价值假设

### 3.1 MVP 必须交付的核心承诺

用户能在一个 Web 任务工作台：

1. 创建研究任务并填写边界（研究问题、竞品、指定网址、排除条件）。
2. 看见将被使用的来源清单，移除不可信或不相关来源。
3. 让 Agent 执行来源采集、事实抽取、逐条证据绑定、对比整理。
4. 在“有证据 / 证据冲突 / 缺证据”状态下审核关键结论。
5. 预览、编辑并手动导出一份 Markdown 研究报告；可追查对应源链接和任务执行事件。

### 3.2 P0 / P1 / Out of scope

| Priority | 功能 | 边界 |
| --- | --- | --- |
| **P0** | 研究 Brief、来源白名单、只读采集、结构化事实、Claim ↔ Source 锚点、冲突与缺证据标记、对比矩阵、人工审阅、Markdown 导出、运行状态/失败重试/成本记录 | 支持英文来源、中文报告；3–5 竞品、最多 20 来源/任务 |
| **P1（验证后）** | 保存研究模板、用户批注历史、报告版本差异、团队分享、CSV 导出、定期更新提醒、许可合规的数据连接器 | 不进入首轮 MVP 成功标准 |
| **明确不做** | 任意电脑控制、多 Agent 编排、浏览器登录/代替付款、自动发送邮件/发布内容、自动下单、竞品实时监控、无限网页爬取、企业 SSO、移动原生 App | 作为后续独立评估项 |

### 3.3 数据接入与商业合规门槛（不可绕过）

- **Hacker News：** 优先考虑其公开检索机制（例如 [HN Search / Algolia](https://hn.algolia.com/help)）获取允许的内容和链接；以实际接入政策和稳定性测试为准。
- **Product Hunt：** [官方 API 文档](https://www.producthunt.com/v2/docs)明确说明默认不得用于商业用途，商业使用应联系官方取得许可。**在取得相应授权前，禁止把 PH API 作为商业 MVP 的自动化数据源，也不得借助绕过限制的抓取作为替代。** 首版允许用户自行添加 PH 页面链接及其合法整理的笔记，标为“用户提供/未自动核验”；或仅跳转用户自行查看。
- **其他公开网址：** 仅处理允许访问的页面，尊重 robots、使用条款与限速；禁止绕过登录、付费墙、反机器人验证；无法合法访问时返回“来源不可用”并要求更换来源。
- **全文保留：** 默认只保留完成证据定位所必需的片段和元数据，遵守许可与删除期限；不得未经授权发布第三方评论全文。

上述条款是**Release Blocker**：获取许可/合法接入路径未确认的来源必须关闭自动导入。

## 4. 端到端用户旅程

### 4.1 Happy path

1. **New research** → 选择“AI/SaaS 竞品扫描”，输入领域、3–5 家竞品、3 个优先问题；可添加种子 URL。
2. **Scope check** → 系统展示工作边界、预估来源上限、允许的数据源与排除规则；用户点击“开始研究”。
3. **Discovery & intake** → 生成候选来源，按来源类型、日期、采集状态分类；用户可剔除来源/补充 URL。
4. **Evidence build** → 将来源转换为结构化 Source + Claim，建立精确片段定位与获取时间；出现冲突/缺证据时不能悄悄补造事实。
5. **Review gate** → 关键事实以“待审”进入清单；用户批准、修改成假设或删除。
6. **Draft** → 生成相同固定结构的竞品对比矩阵、优缺点、用户反馈与待验证机会。
7. **Export** → 用户点击导出 Markdown；报告包含来源列表、时间戳、限制说明与核验状态。

### 4.2 Empty / error / safe states

- **没有竞品：** 阻止开始，给填写示例，不自动虚构品牌。
- **来源不足：** 标记覆盖率不足，允许导出“部分结果”但不标记完成/达标。
- **网页不可获取：** 保留原 URL 和失败类型，允许重新尝试或人工替换，不尝试绕过。
- **两条来源矛盾：** 同时展示原文片段与时间；默认保留冲突状态。
- **API/模型超时：** 按阶段保存进度并可从安全检查点重试；重试不重复来源和计费事件。
- **用户撤销批准：** 重新计算报告审查状态，旧版本不可伪装成已通过。
- **网页包含“忽略指令/发送密钥”等内容：** 视为不可信数据，不改变 Agent 工具权限和任务目标。

### 5.1 关键体验机制

**Source drawer（来源抽屉）：** 点击矩阵任一事实，展开“原话片段 / 来源页 / 发布时间（若有）/ 抓取时间 / 被哪些结论引用 / 审核状态”，支持用户打开原文，而不仅是看到小号脚注。

**Review queue（审核队列）：** 按风险优先排序：价格/数字、含“第一”“唯一”的强断言、涉及竞争者负面评价、发生冲突的事实。对每条事实提供“批准 / 改写为假设 / 排除”。

**Task timeline（任务时间线）：** 阶段级展示 Collect → Extract → Match → Compose → Review → Export；明确何时失败与何时被用户干预。首版不展示伪造的“Agent 心理活动”或并不存在的实时思考链。

## 6. 业务规则与信任策略

### 6.1 Claim 分类

| 类型 | 示例 | 合格证据与呈现 |
| --- | --- | --- |
| **Fact / 事实** | 某产品官方页面列出“团队计划” | 需要直接相关来源 span；展示来源时间与出处 |
| **User voice / 用户观点** | 一位评论者称“配置复杂” | 展示其为个人评论，不得提升为统计共识 |
| **Inference / 分析推断** | 该细分市场存在验证层机会 | 明确写“分析假设”；可链接多个依据但不冒充事实 |
| **Unknown / 缺证据** | 未找到定价或某功能 | 写“未找到/待核验”，绝不生成猜测值 |
| **Conflict / 冲突** | 两个页面对某价格说法不同 | 保留两个证据与时间，等待人工确定口径 |

### 6.2 审核发布规则

- **Draft export：** 允许携带“未验证”水印/说明的草稿导出，以避免锁死工作；禁止出现“已审核”标识。
- **Approved export：** 关键事实必须 100% 经用户批准或剔除；没有出处的推断必须标注“假设”；冲突必须解决或明确披露。
- **外部写操作：** P0 不支持把报告自动写回 Google Docs、Notion、CRM、邮件或第三方平台。
- **用户编辑：** 人工改动关键事实会撤销原批准状态；如果增加了新事实，必须补充证据或标成假设。
- **来源删除：** 删除被引用来源时，相关事实立即变成“来源缺失/待核验”。

## 7. KPI 与成功门槛（全部为预设目标，不是已有结果）

### 7.1 北极星指标

**AER（Accepted Evidence-backed Reports）**：在指定周期内，满足格式/证据门槛、经用户批准且最终被明确“接受为可用”的**不同任务报告数量**。只计一次通过的最终版本；不将草稿、点击“生成”、导出次数算入。

### 7.2 MVP 门槛与分母

| 指标 | 定义 | 预设候选门槛 | 责任/测量方式 |
| --- | --- | --- | --- |
| Critical claim evidence coverage | 已批准的关键事实中，能回到匹配来源 span 的比例 | **100%** | 人工逐条核验；任何不达标禁止 approved |
| All factual-claim evidence coverage | 报告事实句中具可定位来源的比例 | ≥ **95%** | 随机抽样 ≥ 100 句；推断单独统计 |
| Correct source attribution | 抽样的事实-证据对中，证据确实支持该事实的比例 | ≥ **90%** | 两名审核员盲审；分歧仲裁 |
| Usable report rate | 报告经目标用户认为可用于讨论、无需重写 | ≥ **70%** | 真实任务盲评，含失败任务的全部样本作分母 |
| Net human time saved | 相同质量标准下（人工基线分钟−Agent 使用中人工分钟）/人工基线分钟 | 中位数 ≥ **30%** | 计入审阅、纠错、重试时间 |
| Cost per accepted report | 模型+检索+解析等实际可归因变量成本 / AER | 探索目标 ≤ **US$1.50** | 逐任务记录；目标待实测校准 |
| P0 security & policy | 未授权抓取、越权外发、致命 SSRF、绕过审批 | **0 起（阻断门槛）** | 自动化与人工红队测试 |

**注意：** 上述数值均为用于做取舍的*proposed acceptance thresholds*。实际是否可行未知；若多个门槛无法同时满足，应缩小场景或调整成本结构，不得挑选成功案例虚报总体成绩。

### 7.3 第一轮验证设计（建议）

- 受访者：5–8 位目标 ICP，来自至少 3 个团队；首轮为探索性样本，不用于推断整体市场。
- 工作任务：不少于 20 个**真实、不同**的竞品研究 brief；保留人工 baseline、输入、来源集合、执行与人工审阅录屏/记录。
- 对照：在相似范围内由同类用户手工完成，与 Agent 结果采用相同质量评价表；标注学习效应与任务难度差异。
- 负样本：网页不可访问、来源互相矛盾、过期定价、评论包含恶意指令、HTML 中出现提示注入、引用链接失效。
- 决策：必须同时考察质量、真实人工节省、用户愿再次使用/愿付费意愿与安全，不以生成次数或 PH 点赞替代。

## 8. 关键页面与信息架构

**Navigation：** Projects → Research Tasks → Task Workspace → Sources / Evidence / Compare / Report → Export。

| 页面 | 主要内容 | 首要操作 |
| --- | --- | --- |
| Task list | 任务标题、更新时间、状态、最近报告 | 新建 / 继续 |
| Brief form | 研究问题、竞品、种子 URL、限制条件 | 校验并启动 |
| Task workspace | 任务阶段、预计来源量、错误/重试与可用性 | 审查来源 / 取消 |
| Sources | 来源类型、URL、获取时间、可用性、许可标记 | 排除 / 添加 |
| Evidence review | Claim、支持 span、审查状态、冲突警报 | 批准 / 否决 / 设为假设 |
| Report | 对比矩阵、用户反馈、未确认项、时间戳 | 编辑 / 导出 |

移动端仅要求响应式阅读与查看，**不承诺手机上完成高密度证据审核**；桌面端为设计优先。

## 9. 技术方案与非功能要求（产品约束）

### 9.1 建议架构（非唯一实现）

- **前端：** Web App（Next.js/React 或同等），桌面优先、支持可访问性键盘操作。
- **服务端：** API、任务调度/队列、来源接入层、结构化抽取、证据映射、报告渲染；LLM 适配器与策略引擎隔离。
- **数据：** 关系数据库记录任务/来源/事实/审核/审计事件；受控对象存储存导出文件与允许保存的内容片段。
- **Agent 控制：** 固定工作流 + 有界模型调用；每一步使用 JSON Schema 校验输出；最大步骤、超时、费用预算均由后端强制执行。
- **默认权限：** 只读检索；**没有**浏览器登录、shell、任意 HTTP POST、自动发送邮件或访问私有系统的能力。
- **审核门禁：** 由代码检查事实/证据/审核标记，不能依赖模型声明“审核通过”。

### 9.2 非功能验收（P0）

| 维度 | 目标 / 防线 |
| --- | --- |
| 可观测性 | 每次运行唯一 run_id；事件记录阶段、延迟、失败类别和成本 |
| 延迟 | Pilot 目标：≤ 20 来源的任务 P95 生成初稿 ≤ 12 分钟；超出时可保存部分结果（待实测） |
| 稳定性 | 失败后保留已经校验的阶段结果；重复任务/重复回调不重复引用与审计事件 |
| 安全 | URL SSRF 防护（禁止回环/内网/metadata）、严格重定向检查、内容隔离、速率限制、输出净化 |
| 隐私 | 邀请制、按用户隔离、服务端加密密钥、默认不用于第三方模型训练（以实际供应商协议/配置核验后才可承诺） |
| 数据管理 | 试点可删除项目与导出；设定默认保留上限及来源片段删除策略；日志不得记录 API key 或敏感正文 |
| 可访问性 | 核心路径可键盘操作；错误文案可理解；支持基础屏幕阅读器标签 |
| 费用 | 任务级预算硬上限与停机；展示成本估算/实际估算及不可精确计费说明 |
| 合规 | 受平台许可约束的来源无授权即禁用自动采集；不得绕过 robots/登录限制 |

**安全参考：** [OWASP Top 10 for Agentic Applications](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/)。首版安全范围比“通用 Agent”窄得多，但仍需针对间接 Prompt Injection、恶意 URL 和数据泄漏做专项测试。

## 10. MVP 发布计划与责任边界

### 10.1 建议实施节奏（假设 1 PM/Designer + 2 Engineers + 1 QA/兼职）

| Sprint | 重点交付 | 完成定义 |
| --- | --- | --- |
| S0 / 1 周 | 5–8 位用户访谈、5 个真实 brief、人工基线、法务/数据来源评审 | 结论可证伪；明确排除高风险来源 |
| S1 / 1 周 | Brief、任务/运行模型、基础鉴权、只读来源导入 | 正常/失败案例都可追踪 |
| S2 / 1 周 | 结构化事实抽取、来源 span 定位、来源政策/冲突规则 | 可用测试 fixture 验证 claim→span |
| S3 / 1 周 | 审核队列、竞品矩阵、Markdown 生成与导出 | 未经审核不能伪装成 Approved |
| S4 / 1 周 | 质量评测、性能、成本、注入/SSRF 测试、用户可用性测试 | 满足阻断门槛或作 No-Go |

**以上是排期假设，不是工期承诺。** 外部源访问、审计与引用映射可能造成额外工作量；若未过质量门禁，优先减少来源种类/报告字段，而非省略审核机制。

### 10.2 RACI / 最小职责

- **PM：** 问题与范围、试点招募、指标、用户验收及 Go/No-Go。
- **Designer（可兼任）：** Brief、来源抽屉、审核队列、空/错/加载态与可访问性。
- **Backend/Agent Engineer：** 数据接入许可闸门、来源安全、任务/证据/抽取/报告、日志和费用。
- **Frontend Engineer：** 任务工作台、对比与审核交互、导出。
- **QA/Security reviewer：** 测试集、来源溯源正确性、SSRF、权限、红队与回归。

## 11. 主要风险、决策与未决事项

| 风险 | 影响 | 优先缓解 |
| --- | --- | --- |
| 输出“有引用但不支持结论” | 核心产品承诺失效 | span 级对齐 + 人工审核 + 不通过即降级 |
| HN/PH 社区样本偏差 | 错误市场判断 | 明确评论量、时间、平台倾向，不推断全市场 |
| PH API 商业授权问题 | 非法/不稳定来源依赖 | 无授权禁用自动化采集；用户手动提供合法笔记 |
| 模型成本与长任务重试 | 单报告成本过高 | 来源上限、缓存、阶段复用、硬预算上限 |
| Prompt Injection / SSRF | 越权、泄漏与声誉风险 | 工具最小权限、链接校验、非可信内容隔离 |
| 过度设计通用平台 | MVP 难以验证 | 坚持一个 ICP、一类报告、一条工作流 |
| 数据版权与留存 | 许可、隐私、删除风险 | 最小必要片段、明确来源权限、删除策略 |
| 用户不愿付费 | ROI 未证实 | 先验证净节省工时和复购意愿再定价 |

### 11.1 发布前必须回答的产品问题

1. 用户最难核验的是价格、功能还是评论？这决定第一版矩阵的字段优先级。
2. 用户愿意手动补足多大比例的受限来源？若 PH 必须自动化且无法获授权，应改变来源范围或暂停商业化假设。
3. 在何种任务复杂度/资料量下，引用审查反而增加净工作时间？
4. 什么质量和效率水平能让创始人真的把报告用于每周产品会议，而不是“一次体验”？
5. 试点内容是否涉及客户非公开资料？若是，必须单独审查供应商数据处理与使用权限。

## 12. Launch Gate / 最终签收清单

- [ ] 首发 ICP 和主要任务已有真实访谈与任务样本，不仅是二手评论。
- [ ] P0 FR-01–FR-10 功能通过 [详细验收用例](./mvp-functional-spec-2026-11.md)。
- [ ] 关键事实与来源位置 100% 可审，缺证据不可伪装为事实。
- [ ] 未经用户批准，不能出现 Approved 状态或自动对外发送。
- [ ] 来源平台许可闸门、SSRF 防线、注入测试与权限隔离通过。
- [ ] 任务级耗时、人工审阅、费用、失败与重试可测量。
- [ ] 与人工 baseline 对照，形成完整样本分母；通过门槛才准入 Beta。
- [ ] 公开网站上明确标记为“产品方案 / 未上线”，不得暗示已实现。
