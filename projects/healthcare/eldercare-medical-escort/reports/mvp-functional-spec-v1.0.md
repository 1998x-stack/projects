# 老龄社会可信陪诊平台 — MVP 核心功能详细规格与验收（v1.0）

> **文档编号** EM-FS-001 · **日期** 2026-11-09 · **版本** v1.0 · **产品状态** 提案 / 未实现、未上线  
> **依赖** [PRD v1.0](prd-mvp-v1.0.md) · [行业研究](research-2026-11.md)  
> **范围** 单城市、2–3 家相邻医院、低风险常规门诊、人工调度/应急。本文为可交付研发/运营/QA 的功能合同；并非完整医疗风险规程或法律意见。

## 0. Definition of Done 与产品不变量

**最小端到端验收场景**：成年子女为父亲创建常规复诊预约 → 完成基础需求信息 → 工作人员风险筛选 → 老人本人同意服务，并选择是否授权子女看诊疗信息 → 明示报价、合同和支付 → 人工调度核验陪诊员（含备援）→ 现场确认老人身份并执行节点 → 在授权范围内向家属发送状态 → 诊后记录、金额结算、回访和评价 → 所有动作可审计，异常可人工中止。

**服务安全不变量**：
- I01 未完成有效服务同意、风险筛选或人员资质校验的订单不能进入 `ASSIGNED`。
- I02 付款人与服务对象角色分离；没有 `family_share_consent=active` 时禁止向付款人发送具体诊疗信息。
- I03 无一条医疗建议或医嘱解释由平台/AI 自主生成；只能记录实际医务人员表达，标明来源和不确定处。
- I04 每个进行中订单必须有 `dispatcher_id` 与可联系应急人员；发生重大事件立刻进入人工处理。
- I05 价格变更、延时费用、人员改派、就诊地点变化须可见且有确认/拒绝路径。
- I06 任何前端权限状态都必须由服务端再次校验；所有敏感资料访问最小必要并有审计。
- I07 “完成”不代表家属/老人认可全部服务；纠纷、退款和后续处理可以在订单完成后继续。
- I08 所有时间以带时区 UTC 时间戳存储、界面展示落地医院本地时间；事件按服务端时间排序。

## 2. 订单、授权、事件与状态机

### 2.1 订单主状态

```text
DRAFT
  └─> SCREENING_PENDING
        ├─> DECLINED (不适配/无权承接)
        └─> CONSENT_PENDING
              ├─> CANCELLED
              └─> QUOTE_PENDING
                    ├─> CANCELLED
                    └─> PAYMENT_PENDING
                          ├─> CANCELLED / PAYMENT_FAILED（可重试）
                          └─> READY_TO_ASSIGN
                                ├─> CANCELLED (按退改规则)
                                └─> ASSIGNED
                                      ├─> REASSIGNING -> ASSIGNED
                                      ├─> CANCELLED
                                      └─> CHECKED_IN
                                            ├─> INCIDENT_OPEN (暂停正常流程)
                                            └─> IN_SERVICE
                                                  ├─> INCIDENT_OPEN
                                                  └─> SERVICE_ENDED
                                                        └─> COMPLETED
```

订单取消可能发生在多个未结束状态，但不得覆盖真实发生的现场事件。重大事件通过独立 `incident.status` 管理，`INCIDENT_OPEN` 对订单为安全锁定，处理后由授权负责人确认恢复、终止或转人工结案。订单进入 `COMPLETED` 需要人工或服务对象确认并具备必要记录，**禁止通过超时自动“成功完成”**。

### 2.2 并行状态与不可逆记录

- `payment_status`：`UNPAID | PAID | PARTIAL_REFUND | REFUNDED | PAYMENT_FAILED`；不得把退款直接等同订单取消。
- `consent_status`：`UNREQUESTED | ACTIVE | WITHDRAWN | EXPIRED`，按 `service` / `family_share` / `specific_material` 分开。
- `escort_status`：`PENDING_VERIFICATION | VERIFIED | SUSPENDED | INACTIVE`，培训、核验有效期单独记录。
- `incident_status`：`OPEN | ACKNOWLEDGED | ESCALATED | STABILIZED | CLOSED`，严重事件须有复盘记录及审批。
- `support_ticket_status`：`OPEN | INVESTIGATING | WAITING_CUSTOMER | RESOLVED | CLOSED`。

**不可变事件日志**：订单状态每次变化记录 `actor`、时间、旧状态、新状态、原因、来源、关联服务单、策略版本。纠错通过新事件追加，不篡改历史。价格/授权变更为新版本，不在旧版本上静默覆盖。

## 3. F01 预约入口与资料最小化（P0）

**用户故事**：作为工作日无法陪诊的子女，我可以不上传完整病历，为父母创建可报价的陪诊预约；作为不熟悉手机的老人，我可以打电话由客服协助录入。

**输入（必需）**：试点城市、医院院区、日期/集合时间、预约人联系方式、老人基本称呼与联系方式、服务类型、预计时长与集合位置；医院具体科室/就医环节按最低必要收集。就诊实名证件如由医院要求，应由本人妥善保管，不默认上传平台。

**主路径**：选择服务区域 → 填写时间地点 → 选择常规门诊 → 阅读服务边界 → 提交 `DRAFT` → 生成不可预测订单 ID → 进入风险初筛。电话代录入须记录代录入员工及与本人沟通结果。

**异常与边界**：医院不在覆盖范围、时间距当前太近、人员供给不足 → `OUT_OF_AREA / SLOT_UNAVAILABLE` 明确拒绝或人工咨询，不伪造库存；重复提交使用 `idempotency_key` 返回同一订单；与用户确认前不得自动收取额外费用。

**验收**：
- Given 在覆盖范围且资料合法，When 创建预约，Then 返回订单号、费用尚待确认、下一步风险筛选。
- Given 院区不覆盖，When 提交，Then 不生成“可履约”订单，显示人工咨询/拒绝。
- Given 网络重试，When 同一幂等键重复提交，Then 只存在一个订单且不重复支付。

## 4. F02 服务适配与人工风险筛选（P0）

**目标**：识别非医疗陪诊不能承接的任务，而不是做医学诊断。问题表由试点行业顾问及法律顾问审核并版本管理。

**筛选维度**：是否急症征象、意识/认知与有效同意能力、是否需专业转移或持续监护、是否刚接受麻醉/镇静、是否需要用药/注射等医疗操作、行动自理程度、轮椅及楼梯可达性、就医时间与交通条件、是否有陪同人数限制。信息不足时不得猜测“低风险”。

**业务规则**：初筛命中红线 → `REVIEW_REQUIRED` 或 `DECLINED`，给出非诊断性质的原因与人工联系方式；只有**具相应权限的受训调度员**可核验并落地 `ACCEPTED`；所有人工覆盖应记录依据、责任人和是否需要专业顾问签核。急救场景指引求助当地紧急服务。

**验收**：
- Given 表单选中“需要专业医疗监护”，When 提交，Then 不得进入 `CONSENT_PENDING` 或派单。
- Given 关键问题缺失，When 风险复核，Then 标记 `NEEDS_INFO` 而非默认通过。
- Given 风险方案变更，When 查看旧订单，Then 可查看其筛选表版本与操作时间。

## 5. F03 合同、报价与分层授权（P0）

**用户故事**：老人能明确决定是否接受服务、是否愿意家属看到诊后信息；子女能知道总费用、加时与取消规则。

**三个不同对象**：
1. `service_acceptance`：服务对象本人/适格代理的服务范围、人员进入范围、取消权和风险说明；
2. `privacy_notice_ack`：必要数据处理告知；涉及敏感个人信息的同意另行满足适用法要求；
3. `family_share_consent`：可分别允许“行政进度”“就诊待办”“医嘱原话”，默认只开放必要行政信息，医疗内容 **默认不开启**。

**报价**：显式展示基础时长、基础费用、可能的等待/加时单价、可选项、支付方式、取消退款规则、税费（如适用），版本化为 `quote_version`。任何涨价/范围变更需要新的确认，不允许陪诊员现场口头私自加价。合同签订主体、开票及支付主体需与真实履约安排一致。

**授权撤回**：老人可通过本人验证的电话/端内方式随时撤回可撤回的家庭共享；撤回生效后停止后续敏感推送，历史合法留存与法定保存另行说明。服务同意撤回则进入人工安全结束/取消流程，不能把老人留在不安全位置。

**验收**：
- Given 子女已付款但老人拒绝家属看医嘱，When 完成服务，Then 家属端只看行政节点/账单，不得获得诊疗内容。
- Given 老人撤回家属共享，When 后续节点生成，Then 敏感信息不再进入通知队列，已排队消息须再次鉴权。
- Given 报价由 ¥298 改为 ¥360，When 用户未确认新版本，Then 不得扣款或强制加时。

## 6. F04 陪诊人员核验、派单与备援（P0）

**人员主数据**：`escort_id`、身份/联系方式核验状态、岗位培训项目及复核时间、可服务院区、可用时间、非医疗能力边界、当前状态、事故/投诉复训限制。不得展示敏感证件全文给患者端。

**派单流程**：风险结果 `ACCEPTED` + 有效服务同意 + 价款/合同确认 + 必要支付完成 → 调度员选择已核验且空闲人员 → 系统校验排班冲突、院区、行程间隔、资质状态 → 人员确认 → 分配备援与应急联系人 → `ASSIGNED`。默认**人工派单**，排序建议不能直接生效。

**改派/爽约**：人员临时不可达，订单转 `REASSIGNING`，必须在规定内部响应目标内联系备援并主动告知老人/家属；未经同意的服务范围变化不可私自执行；无安全替补即提前告知取消与退款，不用虚假的“已派单”占位。

**验收**：
- Given 员工状态 `SUSPENDED`，When 调度派单，Then 服务端拒绝并记录原因。
- Given 两个订单时段冲突，When 同一陪诊员被重复分配，Then 后端以原子性校验拒绝。
- Given 已派单人员迟到，When 到场承诺时间超过阈值，Then 调度看板报警，并记录实际迟到用于 KPI 分母。

## 7. F05 现场身份核对、签到、节点与诊后回顾（P0）

**现场检查清单**：工作人员主动报姓名/机构/订单核对口令；核对现场服务对象身份并确认被允许陪同；复核医院流程与联系方式；确认行动协助方式及隐私意愿。不使用拍摄老人证件或公开医疗号码来替代身份核对。

**事件节点（最小集）**：`ESCORT_EN_ROUTE`、`ARRIVED`、`PATIENT_VERIFIED`、`WAITING`、`CLINIC_VISIT_FINISHED`、`PHARMACY_OR_TEST_FINISHED`、`HANDOFF_COMPLETED`。只记录时间和必要备注，不记录泛化实时定位轨迹。节点未发生不得预打卡；离线缓存要保留真实事件发生时间与提交时间。

**诊后内容**：只收集医院纸质/电子原始材料允许整理的事实；标注 `source_type=clinician_verbatim|hospital_material|customer_statement`；不确定内容标记 `unclear_needs_confirmation`。陪诊员不得补写诊断结论。录音录像默认禁用，需医院允许且满足合法同意才能另行设计。

**验收**：
- Given 未核对老人身份，When 试图开始院内服务，Then 拒绝进入 `IN_SERVICE`。
- Given 员工标记完成但缺少交接确认，When 点击结束，Then 提示补充安全交接或走人工例外。
- Given 诊后记录内容无来源/权限，When 发送给家属，Then 系统阻断并转人工复核。

## 8. F06 按授权推送与双通道适老通信（P0）

**渠道**：家属微信模板消息/短信（按可用性与授权）、老人电话人工确认；涉及健康信息的通知默认仅显示“有待查看信息”，需进入鉴权页查看，不在短信正文暴露病情。

**事件**：人员确认、预计到达、到场、流程关键节点、延迟、改派、事件处理进展、服务结束、售后工单。模板与提醒频率由后台配置；避免向家属频繁广播病情。

**发送前二次鉴权**：即使消息在授权时已入队，也须在**实际发送时**重新检查 `consent_status`、收件人的订单权限和数据等级。撤回共享后不能继续发送敏感消息。

**验收**：
- Given 老人未授权医疗共享，When 生成诊后节点，Then 家属仅看“服务结束”的行政状态。
- Given 手机号码误输或验证失败，When 推送，Then 禁止向未经确认的新号码发送敏感通知。
- Given 外部消息平台故障，When 发送失败，Then 保存失败码并进入人工待处理队列，不默认为送达。

## 9. F07 安全事件、拒接/转介与紧急响应（P0）

**触发**：工作人员一键“异常/紧急求助”、服务对象反馈、调度发现联系中断、迟到超阈值、疑似隐私泄露、发生跌倒/突发不适等。严重程度是运营优先级，不是临床诊断结果。

**处理链**：`OPEN` 自动指定值班责任人 → 严重问题直接寻求医院现场救助/120 → 人工回拨并记录 → 通知依法/授权可联系的人 → 决定暂停、转介、结束或恢复 → 专人结案与复盘。**不得用“等待后台审批”延误现场急救**。

**事件必要字段**：`incident_id`, `order_id`, `reported_at`, `reporter_role`, `incident_type`, `severity_operational`, `owner_id`, `actions[]`, `outcome`, `review_due_at`；诊疗信息另受敏感权限约束。

**验收**：
- Given 现场人员按“紧急求助”，When 提交，Then 立即显示“优先就地求助医院/急救”指引和已知应急电话，同时生成工单并通知当班负责人。
- Given 工单未被确认，When 超过内部响应目标，Then 触发上级 escalation，不能静默关闭。
- Given 订单关联严重事件，When 试图直接关闭订单，Then 必须先由授权负责人审核安全状态和交接记录。
- Given 系统离线，When 点击求助，Then 仍展示可直接拨打电话及离线 SOP；不能依赖后台才能求助。

## 10. F08 支付、完单、退改与消费者支持（P0）

**账单原则**：先明示服务方案与价格；支付流通过合规支付服务商，不保存卡号/支付密码；Webhook 验签并具备幂等键。现金或线下支付试点必须由合规主体处理并有可核对财务凭证，禁止私下向陪诊员转款作为平台承诺服务的必要条件。

**价格项**：基础服务费、同意的增项/加时、优惠、税费（如适用）、实收、退款和最终净收入独立记账。加时必须先说明金额/可选处理方案，长时间候诊不可悄悄计费。

**取消与退款**：按服务合同版本和实际履约阶段明确规则。平台原因取消或人员缺席优先全额退款/补救并保证老人安全交接；老人已经到场的取消不得简单套用“超时不可退”格式条款。人工客服可发起争议审查，客服无权私改原始账单。

**验收**：
- Given 支付平台重复回调，When 同一 `provider_transaction_id` 到达两次，Then 账务只入账一次。
- Given 平台因人员缺席无法履约，When 取消，Then 生成全额退款待办、客服回访与事故复盘；不得算作成功订单。
- Given 用户请求查看退款进展，When 打开订单，Then 可查看申请、处理、原路返回状态及相关说明。

## 11. F09 运营看板、质检、权限与审计（P0）

**调度看板**：按院区/日期查看风险筛选、未授权、待派、临近到场、进行中、异常、待回访；每个订单有明确 owner 和下一次处理时间。调度员仅能看对应服务区域与任务。

**质检**：独立回访采用不诱导问卷，记录首次被访谈者和支付方/服务对象身份差别，保留差评原文及处理结果；事故、投诉、改派、超时单必须可抽检。订单发生时间、到场承诺时间、实际到场、综合人员占用、获客来源及实际成本需被可靠记录。

**安全**：后台 MFA、角色/订单/地区访问控制、敏感字段遮盖、日志脱敏、上传格式白名单、带版本的隐私策略；审计关键事件不可由一般客服删除。个人信息访问导出需审批、可核查。

**保留/删除**：由法律审查确定分类型期限，原则上数据最小化、保留到期清理、备份清除有可测试窗口。用户撤回可撤回授权后停止未来处理；必要法定记录存留须注明依据和处理范围。

**验收**：
- Given 非本区域调度员，When 直接请求其他区域订单 API，Then 返回 403 且记录审计。
- Given 家属撤回共享，When 客服查询医嘱，Then 若无独立正当业务必要则拒绝，不能“客服权限”绕过。
- Given 隐私数据导出，When 发起请求，Then 需有审批/有效业务目的及最小数据集，生成访问日志。
- Given 月度报表，When 计算贡献毛利，Then 能按单追溯真实收款、退款、实际工时、人工变动成本与获客来源。

## 13. API / 事件合同（示意，非已部署接口）

| 方法 | 路径 | 权限与关键效果 |
| --- | --- | --- |
| `POST` | `/v1/orders` | 付款人/老人创建草稿；幂等 |
| `POST` | `/v1/orders/{id}/risk-review` | 受训调度员审核，附规则版本 |
| `POST` | `/v1/orders/{id}/consents` | 经过本人/代理核验写入授权证据 |
| `POST` | `/v1/orders/{id}/quotes/{version}/accept` | 确认特定费用版本 |
| `POST` | `/v1/orders/{id}/assignments` | 调度员派/改派，原子性冲突校验 |
| `POST` | `/v1/orders/{id}/events` | 已派陪诊员提交现场事件 |
| `POST` | `/v1/orders/{id}/incidents` | 现场异常，触发人工通知 |
| `GET` | `/v1/orders/{id}/timeline` | 视角色与有效授权返回脱敏时间线 |
| `POST` | `/v1/orders/{id}/visit-notes` | 经授权的诊后原话/事项记录 |
| `POST` | `/v1/orders/{id}/closeout` | 完单+服务交接审查 |
| `POST` | `/v1/orders/{id}/refund-requests` | 售后退款申请，保留审核链 |
| `GET` | `/v1/ops/queue` | 区域/权限过滤的调度与异常队列 |

**所有写入要求**：认证、服务端授权、参数校验、请求追踪 ID、幂等键（涉及支付/派单/事件）、避免重放、统一错误码；不在 URL、普通日志或分析事件中嵌入姓名、病症或医嘱。Webhook 必须验证签名和交易所有权。

**建议错误码**：`AREA_UNSUPPORTED`, `SLOT_UNAVAILABLE`, `RISK_REVIEW_REQUIRED`, `SERVICE_CONSENT_MISSING`, `FAMILY_SHARE_FORBIDDEN`, `ESCORT_UNVERIFIED`, `ASSIGNMENT_CONFLICT`, `QUOTE_CHANGED`, `STALE_ORDER_VERSION`, `INCIDENT_LOCKED`, `PAYMENT_PROVIDER_ERROR`。服务端错误不应让订单悄悄跳到下一状态。

**关键领域事件**：`order.created`, `risk.reviewed`, `consent.granted`, `consent.withdrawn`, `quote.accepted`, `assignment.confirmed`, `assignment.failed`, `escort.arrived`, `incident.opened`, `incident.escalated`, `service.ended`, `payment.refunded`。事件用于状态同步及运营警报，**不**通过数据分析 SDK 广播健康信息。

| 领域 | MVP 目标 | 测试方法 |

## 15. 测试矩阵、发布门禁与反例

### 15.1 发布前必须通过的 E2E 场景

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| T01 | 常规门诊本人同意、授权家属看行政进度 | 完成预约→派单→签到→节点→结算闭环 |
| T02 | 付款人支付但老人拒绝共享医嘱 | 付款人看到金额和进度，看不到诊疗内容 |
| T03 | 老人中途撤回家庭分享授权 | 即时阻断未来健康信息消息和查询 |
| T04 | 筛选出现需专业护理/急症征象 | 停止派单，人工转介，不自动判“可陪诊” |
| T05 | 人员临时缺席或迟到 | 看板升级、联系备援、主动告知与补救/退款 |
| T06 | 到场发现服务对象不一致 | 禁止开始；人工核验或安全取消 |
| T07 | 现场触发紧急情况，后台断网 | 仍显示急救电话/现场求助指引；恢复网络后补事件 |
| T08 | 订单报价变化未确认 | 拒绝收费变更，要求再次同意 |
| T09 | 并发重复派单及支付回调重放 | 只产生唯一有效分配及唯一账务 |
| T10 | 跨家庭、跨区域直接猜测订单 ID | 403/404，不能返回敏感信息 |
| T11 | 客服尝试查看非必要医嘱、导出全量病历 | 服务端拒绝并记录审计 |
| T12 | 退款后报表重新计算 GMV / 净收入 | 账单和报表一致，退款单不计成功付费闭环 |
| T13 | 服务已完成后提出投诉 | 允许创建工单与事故复盘，不篡改完成记录 |
| T14 | 号源“加急办理”或让陪诊员给用药建议 | 产品明确拒绝，人员 SOP 有升级处理 |
| T15 | 订单关联未结重大安全事件 | 不允许一键正常完单，不允许隐匿事件 |

### 15.2 安全闸门

- 每个真实服务对象存在有效服务同意与已审查的风险记录；没有缺口。
- 试点所需服务合同、人员核验、保险与用工安排经适格专业人员审查。
- 100% 关键角色/订单访问路径有服务端权限校验，负例测试不得泄漏健康信息。
- 一次紧急事件桌面演练和一次现场演练经负责人签字复盘。
- 试点没有开放的 P0/P1 安全缺陷；出现真实严重事故或未经授权共享则立即暂停相关服务。
- 建立可公开解释的加时、取消、退款、投诉服务条款，不依赖“同意即免责”。
- 可追溯单笔真实成本与投诉/迟到记录，不能通过删除失败订单美化指标。

## 16. 首版实施切分（推荐）

| 阶段 | 实现范围 | 依赖/出口 |
| --- | --- | --- |
| G0 运营台账 | 合规授权和合同模板、风险表、人员核验、人工接单、紧急联系人 | 先确认能依法安全地做 10 单 |
| G1 核心业务 | F01–F04：创建/审核/同意/报价/派单、身份权限 | 测试 T01–T05 |

| G3 交易与治理 | F08–F09：支付/退款、客服、审计、数据权利 | T09–T15 + 综合验收 |
| G4 受控试点 | 逐单评价、工时和 CAC 账本、90 天实测 | 达成 PRD 第 7/10 章门槛后再讨论规模化 |

**明确不在 G0–G4**：全自动 AI 医疗建议、住院护理、术后专业护送、全国多城即时撮合、医院 HIS 集成、预测疾病、诊室直播、默认录音、积分与会员商城。
