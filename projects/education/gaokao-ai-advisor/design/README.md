## 1. 设计总判断

**产品不是“再生成一个冲稳保报告”，而是“审计用户已有的志愿草表，并让每一个关键结论能追溯到官方依据”。**

从风险控制出发，首版按如下顺序设计：**合法官方来源与版本 → 确定性报考规则 → 历史数据可比性 → 个人偏好 → 受约束的 LLM 解释 → 人工复核与导出**。任何模型生成内容都不能替代招生资格、当年计划、专业组代码或正式考试院操作。

## 3. MVP 全链路

~~~mermaid
flowchart TD
 U[考生输入画像/已有志愿草表] --> F[React TS 工作台]
 F --> API[FastAPI + 资源级鉴权]
 API --> PG[(PostgreSQL: snapshots/drafts/audits)]
 P[人工审核官方计划/政策] --> C[版本化 Catalog + RulePack]
 C --> W[Python Worker]
 PG --> W
 W --> R[三值硬规则 + coverage]
 R --> H[历史位次可比性 + 偏好提醒]
 H --> L[可选只读 LLM 解释校验/模板回退]
 L --> PG
 PG --> API
 API --> X[带来源版本和水印的辅助草表导出]
~~~

关键的是**数据源和规则版本先于模型**。如果某年招生计划、专业组或限制条件不能合法取得并核实，本年度硬性“可报”结果必须停用；历史练习可以保留，但它不能被呈现成当前志愿建议。

## 4. 三端共享工程不变量

1. **单一试点范围**：一个省份 × 一个普通本科批次 × 一种志愿单位类型；在实施前选定并审定具体地方规则。专业代码、专业组代码均是字符串，保留前导零。
2. **数据版本冻结**：每次审计固定 profile_snapshot、draft_revision、catalog_snapshot、rule_pack 与 engine_version；变更导致 STALE，不能把多版本拼成一个结论。
3. **三值资格**：ELIGIBLE / INELIGIBLE / UNKNOWN；UNKNOWN 不是 PASS，ELIGIBLE 不是“录取概率高”。
4. **工作流状态独立**：QUEUED / RUNNING / COMPLETED / FAILED / STALE 仅表示运行进度。COMPLETED 也可能含 BLOCKER 和 UNKNOWN。
5. **可比历史而非伪预测**：仅显示历史相对位次（有条件时）；数据口径变更则 NOT_COMPARABLE；未经时间前推回测和概率校准不显示数字录取率。
6. **解释不可裁决**：LLM 只能消费只读事实摘要，输出受 schema 与来源核验约束的解释；失败时回退模板，不改变硬规则状态。
7. **官方来源可见**：关键资格依据引用具体官方 URL、文档日期、版本、段落/表格锚点；许可、完整性未审查不允许激活。
8. **权限与隐私**：workspace 级授权；不采集考试院密码；学生位次/偏好不进入 URL、通用日志、第三方分析；未成年人数据处理需事先法务核查。
9. **仅辅助导出**：可以下载带警示的人工核对草表，不允许官方自动提交。前端、API、导出三个地方一致表述。
10. **可信状态 UI**：当前数据无法核实/旧审计/计算失败时显式阻断当年“可报”结论，不能“默认绿色”。
11. **可重复审计**：golden fixtures、源 hash、规则版本、输入 fingerprint 和审计覆盖记录可回放；关键错 PASS 为发布阻断。
12. **发布阶段诚实**：Markdown 出版≠代码实现≠已通过测试≠正式运营。

## 5. API/状态映射

| 业务状态 | 后端 enum | UI 显示 | 算法依据 |
| --- | --- | --- | --- |
| 当年来源已核验 | CURRENT_VERIFIED | 当年官方数据已按版本审查，仍需最终官方核对 | 来源快照核验与激活 |
| 只有历史来源 | HISTORICAL_ONLY | 历史练习，不能指导当年真实填报 | 当年 snapshot 缺失 |
| 未核实硬条件 | UNKNOWN / NEEDS_INPUT | 无法确定，补资料或人工核对 | 三值规则缺输入/未覆盖 |
| 明确不符合 | INELIGIBLE / BLOCKED | 存在已确认不符项及其官方依据 | FAIL 结果与 source_ref |
| 任务完成但需核验 | COMPLETED + NEEDS_INPUT | 检查完成，不等于可以填报 | 审计完成与资格分离 |
| 草表或政策变更 | STALE | 旧结果已过期，请重新核验 | fingerprint/catlog/policy revision |
| 模型无法解释 | Explanation FAILED | 使用模板解释，保留规则证据 | LLM 与规则解耦 |

> 算法内部来源等级 VERIFIED_CURRENT 映射成公开 API 的 CURRENT_VERIFIED。此处公开 API enum 为客户端单一真值来源。

## 6. 为什么这样拆算法、后端、前端

- **算法**：保证可解释的、可测的“已核验/不符/未知”逻辑；计算结果只依赖固定来源与规则，容易构造对抗测试。
- **后端**：保证版本完整性、授权、事务、状态和删除；所有“谁能看见哪些孩子的数据”“什么时候变为 STALE”只能后端裁定。
- **前端**：保证用户能发现风险、读懂未知项、点开来源和安全地修改草表；UI 不能用漂亮的绿灯替代事实性校验。
- **共享契约与测试**：强制字段、状态、文案、错误码一致，避免工程阶段各自演化出“不同的通过定义”。

## 8. 研发顺序与 Go / No-Go

建议以**纵向薄切片**推进：

1. **M0 数据与规则可得性**：先从官方渠道取得允许合法使用的原始招生数据，确定试点省份/批次/单位，并由政策审核员签核，做 500 条关键字段双人对照和 200+ 规则案例计划。
2. **M1 可运行闭环**：先用合成数据实现一条明确选科冲突，从草表编辑到 BLOCKER+source_ref+有警示导出的全链路，完全不必使用 LLM。
3. **M2 规则与历史**：入库版本化数据、完善 UNKNOWN/NOT_COMPARABLE/版本失效/人工复核，执行防信息泄漏的按年回测。
4. **M3 可选模型**：加只读 LLM 解释与拒绝/回退策略，并通过 prompt injection/数值编造/引用伪造测试。
5. **M4 真实用户与发布评审**：隐私和未成年人信息处理复核、安全测试、专家盲审、考生家长对照任务，再决定是否开放本年服务。

**Go**：官方数据范围合法明确、关键规则测试无错 PASS、来源完整、版本失效和授权测试通过、关键用户任务实测有效。  
**No-Go**：仅有网络零散数据、政策规则无法验证、模型会编造当年计划、团队不能把结果风险说清楚。此时退回历史查询/草表学习，而非强推可报结论。

## 9. 文档管理与变更控制

- 规则、schema、后端、前端发生语义变更时，按 **契约 → 算法/后端/前端 → 测试 fixture** 顺序同步；登记省份、年份、影响的 Fxx/Txx 和 ADR。
- 文稿里所有示例院校/代码、日期、当年数据均为**示意**，不得被当作真实当年招生资料；如需用真数据，引用并注明官方来源和版本。
- 公开仓库中的源码如将来涉及考生信息，一律只使用合成样例数据；禁止提交真实考生画像、账号或考试院凭证。
- 修改为“已上线”“已验证”的项目阶段前，必须提供真实测量、部署、来源签核证据。**当前仅是设计稿。**
