## 0. 前端的产品命题

**不是让考生“再问一次 AI”，而是把多方给出的志愿草表变成能看懂、能核对、能讨论的决策工件。** 信息结构顺序始终为：官方事实和范围 → 可确定的限制 → 历史位置及其缺口 → 个人偏好 → 人工确认。

用户每一步都能回答：
1. **这是哪一年、哪个省份、哪个批次的数据？**
2. **这条提醒来自哪一条可点开的官方文件？**
3. **哪些确定不满足、哪些还不能判断？**
4. **我改了考生条件或志愿顺序，之前的结果还有效吗？**
5. **这份文件是否可以拿去省考试院提交？** 答：**不能**；必须自行到官方渠道核对、填报。

首版支持：一个省份 × 一个批次 × 一种志愿单位；当年官方数据不完整则只提供明确标识的历史学习/草表检查，不做当年资格通过宣称。前端不判断 eligibility，也不承诺预测结果。

## 1. 目标角色与用户任务

| 角色 | 典型目标 | 主要风险 | 对应体验 |
| --- | --- | --- | --- |
| 考生 | 核对学校/专业组合是否满足政策和兴趣 | 误信看似确定的“稳” | 来源可点、限制明确、未知不隐藏 |
| 家长 | 比较孩子/家人提供的两套名单 | 将偏好争论混成录取概率 | 同屏对比“事实/偏好/未知项” |
| 学校升学老师（后续） | 辅助复核大量草表 | 误认为软件可替代考试院公告 | 来源与版本明细、可打印审阅摘要 |
| 平台政策审核员（内部） | 核对当年数据和变更 | 旧公告覆盖新公告 | 独立的受限后台，不在学生 UI |

**首版路线**：先完成一个考生个人单账号草表审计。家庭协作为 P1，在访问控制、邀请同意和权限提示完成后再开放；单纯“共享链接可看孩子位次”不可上线。

## 2. 技术栈与前端边界

| 层 | 推荐 | 原则 |
| --- | --- | --- |
| SPA | React + TypeScript (strict) + Vite | 结构清楚，构建轻量 |
| 路由 | React Router | 前端路由守卫仅用于体验；服务端仍做授权 |
| 数据缓存 | TanStack Query | 服务端是 canonical truth，成功写入后 invalidate/refetch |
| API 客户端 | 从 OpenAPI 生成的 TS 类型与请求封装 | 共享 enum，禁止复制/重新命名业务状态 |
| 表单 | React Hook Form + Zod | 字段提示不替代服务端选科/政策判定 |
| UI 组件 | 语义化组件 + CSS tokens（可基于 Radix primitives） | WCAG 2.2 AA 作为目标，键盘优先 |
| 表格/列表 | 小数据量原生 table + 虚拟化按测量引入 | 代码字段复制保留前导零；移动端可滚动 |
| 测试 | Vitest + React Testing Library + Playwright + axe | 对照 API 契约、错误态和可访问性测试 |
| 监控 | 错误码、性能、交互漏斗（脱敏） | 不收集成绩、位次、姓名、志愿明细到分析平台 |

**Local state** 只存筛选、焦点、未提交编辑、弹窗状态；**Query cache** 保存服务器结果的短生命周期视图；**Server canonical** 保存 profile snapshot、draft_revision、audit_id、source/rule版本。禁止把敏感画像写入 localStorage、URL query string、第三方 analytics 事件。

## 3. 信息架构与路由

| 页面 | 路由（示意） | 关键问题 |
| --- | --- | --- |
| S01 Scope & Profile | /start | 我使用的是什么省份/年份/批次规则？哪些信息是必填？ |
| S02 Draft Builder | /drafts/:id | 我有哪些志愿单位，顺序/代码是否正确？ |
| S03 Risk Audit Workbench | /audits/:id | 哪项确定不符、哪项不清楚、证据是什么？ |
| S04 Comparison | /drafts/:id/compare | 改变偏好/草表后两份方案差在哪里？ |
| S05 Export & Source Review | /drafts/:id/export | 当前结果是否过期？能否用于人工复核？ |
| P1 Family Collaboration | /workspaces/:id/members | 谁能看见个人信息，双方意见在哪里不同？ |

## 4. 全流程用户旅程

~~~mermaid
flowchart TD
    S01[确认试点范围 + 创建考生画像] --> C{来源可用于当年判定?}
    C -- 否 --> H[历史练习模式 + 明显年份标签]
    C -- 是 --> S02[导入或编辑已有志愿草表]
    H --> S02
    S02 --> V[校验代码格式/草表 revision]
    V --> A[提交审计任务 202 QUEUED]
    A --> P[轮询状态 RUNNING]
    P -->|FAILED| E[保留草稿 + 修复建议]
    P -->|COMPLETED| S03[按 BLOCKER / UNKNOWN / WARNING 阅读]
    S03 --> S04[比较与修改]
    S04 -->|草表变化| S02
    S03 --> S05[辅助草表导出 + 官方提交提醒]
    S03 -->|STALE| S02
~~~

**状态文案强约束**：
- 202/QUEUED = “已排队开始核验”，不是“核验成功”。
- COMPLETED = “已完成本次检查”，不等于“所有志愿符合条件”。
- ELIGIBLE = “所覆盖的硬规则未发现不符合项”，不等于录取有保障。
- UNKNOWN = “因信息缺失/来源冲突暂无法判定”，用户必须看见待确认清单。
- HISTORICAL_ONLY = “历史资料练习，仅供参考，不能用于本年度填报依据”。
- STALE = “草表/考生条件/官方规则已变化，请重新核验”。
- REVIEWABLE = “本次已覆盖项目可供人工复核”，不等于“可直接提交”。

## 5. S01｜范围与考生画像

### 5.1 字段及默认值

页面首先由 GET /v1/capabilities 读取支持范围（省份、考试年度、批次、志愿单位类型、是否 CURRENT_VERIFIED），**不自行列出全国地区并暗示全部支持**。默认不替用户选择考试年份或专业要求；选择后展示政策状态与“我理解这不是官方填报系统”的确认。

表单建议分两步：
1. **基础条件**：省份、年度、批次、选科、位次或分数输入；位次字段允许不填，但历史比较会受限；给出明确的字段口径和格式例子。
2. **偏好**：地区/费用/专业兴趣与无法接受的选项，全部可跳过；这些是偏好而非限制性报考资格的法律断言。涉及体检等个人情况仅在规则必需时请求最小信息，并给出“暂不提供 → UNKNOWN”路径。

**异常处理**：未支持省批次→OUT_OF_SCOPE 信息页（官方入口 + 数据不可用原因）；当年来源未审核→历史学习模式，不显示“开始当年审计”；选科与规则不兼容→定位字段+解释；敏感信息请求前提供用途/留存/删除说明。

### 5.2 可视化状态提示

| 来源状态 | 文案 | 可用按钮 |
| --- | --- | --- |
| CURRENT_VERIFIED | “本范围的当年官方资料已按版本核验；仍需考生最终查阅官方公告” | 创建当年草表 |
| HISTORICAL_ONLY | “仅有经核验的历史数据，不能用它认定本年志愿是否合格” | 开始历史练习 |
| PARTIAL | “部分条件或计划未核实；本年度结论不可用” | 查看数据缺口 / 历史学习 |
| OUT_OF_SCOPE | “该省份/批次尚未支持” | 官方入口 |

前端不以来源标绿决定是否有资格进入正式“已核验草表”；具体可用能力始终由 capabilities 和审计结果双重约束。

## 6. S02｜志愿草表编辑器：先导入已有方案

输入方式 MVP：手工录入院校代码/志愿单位代码、名称检索（**仅官方目录快照**）、有序调整；可提供限定 CSV schema 的导入，但不在首版支持图片 OCR、PDF 截图识别、第三方平台粘贴自动识别或 AI 猜代码。

~~~text
我的志愿草表 · v4  | 2027 / 试点省 / 普通本科
来源：目录 2027.06.XX（示例）   状态：待再次核验
────────────────────────────────────────────────────────────────────
顺序 │ 院校代码 / 学校       │ 志愿单位代码 / 说明          │ 操作
  1  │ 0001 / 示例院校 A     │ 0A / 示例专业组（纯示例）     │ 上移 下移
  2  │ 0023 / 示例院校 B     │ 01 / 示例专业组（纯示例）     │ 上移 下移
────────────────────────────────────────────────────────────────────
+ 添加志愿单位   导入 CSV（可选）           [开始核验]
提示：代码保留前导零，示例不代表真实招生代码
~~~

**编辑行为**：
- 搜索来自 admission_units 只读接口；展示年份、批次、类型和源；不存在时只允许“标记待核实”，不能 AI 自动修正成任意似是而非的志愿。
- 草表保存使用 expected_revision（CAS），409 VERSION_CONFLICT 显示服务器新旧版本差异，由用户选择手动重放修改；不自动吞并风险相关字段。
- 拖拽排序必须提供键盘“上移/下移”按钮与屏幕阅读器状态；每次保存新 revision。若存在旧 audit，立即显示 STALE；不要保留旧绿色结论。
- 根据省份规则配置提示志愿数量、志愿单位结构；超限不应自动截断或隐藏最后一项，而是返回 BLOCKER/INVALID_ADMISSION_UNIT 等明确错误。
- 允许暂存未完善草表；“可以保存”不等于“能够通过审计”。

建议桌面布局为 **左 55% 志愿清单 + 中 25% 核验状态 + 右 20% 来源与行动**（仅为 UX 初稿，需真实测试）；移动端使用分段 Tab，但同样保留证据跳转与待确认项。

│                            │                      │                      │

### 7.1 审计卡契约

每张 finding 卡只用 API 字段渲染：
- **标题**：错误代码对应的稳定本地化词典，比如“选科条件不符”（不自由生成业务状态）。
- **状态**：BLOCKER / WARNING / INFO；相应资格 ELIGIBLE / INELIGIBLE / UNKNOWN 由服务端提供。
- **为什么**：可信事实摘要 + 适用规则 + 最少一个可核验官方 source_ref；缺少则显示“来源缺失，不能作出确定结论”。
- **历史部分**：不承诺录取概率。以 2023/2024/2025 等真实可比年份列原始最低位次、用户位次、年份、差值与变更标记；数据不可比就显示 NOT_COMPARABLE。
- **下一步**：补信息、联系高校/省考试院核实、移除此项或保留待确认。前端不得一键自动替用户更改全部草表。

### 7.2 状态矩阵

| 状态 | 标题/屏幕语义 | 主行动 | 不可出现 |
| --- | --- | --- | --- |
| QUEUED/RUNNING | “正在检查官方资料及规则” | 继续等待/安全离开 | 已通过/无需检查 |
| COMPLETED + BLOCKED | “检查完成，存在明确不符合项目” | 查看并处理 BLOCKER | 绿色总分 |
| COMPLETED + NEEDS_INPUT | “检查完成，部分项目不能确定” | 补充信息/人工核实 | 默认为可报 |
| COMPLETED + REVIEWABLE | “检查完成，可供进一步人工核对” | 查看来源、下载草表 | “已获录取”“可直接提交” |
| FAILED | “系统未完成核验” + request_id | 重试 | 无风险 |
| STALE | “数据或草表已变更，旧结论过期” | 重新审计 | 旧通过状态仍有效 |
| HISTORICAL_ONLY | “历史练习结果（非当年）” | 查看历史记录 | 2027 当年可报结论 |

### 7.3 来源定位

点击证据链接会打开官方 allowlist URL（应以安全方式新标签打开），并展示文档发布日期、访问日期、对应条款/页码/表格锚点、平台登记的 hash 或来源版本。外部官方页面内容可能变更，因此提供**“链接已失效/版本已变更”**反馈入口，不尝试用模型复述替代已变化的官方公告。第三方页面不得冒充官方来源。

## 8. S04｜方案对比与偏好调整

对比页先覆盖**同一人草表两个版本**，P1 再支持家庭意见。差异视图只显示：
- 新增/删除/顺序调整的志愿单位；
- BLOCKER/UNKNOWN 数量变化以及引用的政策版本；
- 历史位次是否保持可比；不把“风险变低”简化为无依据百分比；
- 用户声明的个人偏好冲突（地域、专业、费用、不可接受条件）；
- 修改导致的旧审计 STALE 标记。

**不同官方快照/规则版本的审计不能直接比较成“进步了 5 分”**；要先显示“数据口径已变更”并允许用户按新版重新检查两份草表。费用与学费若没有官方来源则标 UNKNOWN，不能由 LLM 填猜测值。

交互采用两栏差异卡 + 底部“下一步核对事项”，而不是把用户送到持续聊天的黑箱里。每个“更好”的偏好判断都应能看见用户先前设定，允许用户重设权重。

## 9. S05｜导出、版本与官方入口

导出前显示固定摘要：
- 草表 revision / audit_id / catalog_id / rule_pack_id / 审计时间；
- **是否当年 CURRENT_VERIFIED**；
- BLOCKER、UNKNOWN、WARNING 清单与用户尚未完成事项；
- 官方来源入口，特别是省级考试院和高校章程；
- 明确说明“这是辅助草表，不代表已提交/被录取”。

导出按钮可以在 BLOCKED/NEEDS_INPUT 状态提供**“下载带警示的核对草表”**，不得使用“提交成功”“一键正式填报”“安全入档”等文案。导出前台收到 202 只显示“生成中”；等 GET /v1/exports/{id} 报 COMPLETED 且返回服务端授权的短时下载地址后再展示下载入口。浏览器不根据旧 UI 缓存离线生成正式报告。

个人数据删除页显示删除范围、备份处理政策及执行状态，不能将浏览器清缓存当成服务器删除。

## 10. 前端状态、类型与 API 调用模式

**状态层次**：
- remote：ProfileSnapshot、DraftRevision、AuditRun、Findings、SourceRef、Export；
- local：selectedFindingId、filters、foldedSections、draftInputBuffer、compareSelection；
- capabilities：server 回传当前允许动作/范围；并不代替后端鉴权。

~~~typescript
type EligibilityStatus = "ELIGIBLE" | "INELIGIBLE" | "UNKNOWN";
type AuditRunStatus = "QUEUED" | "RUNNING" | "COMPLETED" | "FAILED" | "STALE";
type OverallReadiness = "REVIEWABLE" | "BLOCKED" | "NEEDS_INPUT" | "OUT_OF_SCOPE";
type SourceScope = "CURRENT_VERIFIED" | "HISTORICAL_ONLY" | "PARTIAL" | "OUT_OF_SCOPE";

function auditHeading(status: AuditRunStatus, readiness?: OverallReadiness): string {
  if (status === "FAILED") return "检查未完成，请重试";
  if (status === "STALE") return "当前结果已经过期，请重新核验";
  if (status !== "COMPLETED") return "正在核验，尚无结论";
  if (readiness === "BLOCKED") return "存在确定不符合项目";
  if (readiness === "NEEDS_INPUT") return "有尚未核实的限制条件";
  if (readiness === "REVIEWABLE") return "已完成覆盖项检查，仍需官方核对";
  return "本范围不支持当年核验";
}
~~~

这段是 UI 示例，不应维护手写枚举作为唯一真值；生产环境从已发布的 OpenAPI 生成类型。用户更改任一关键资料后，前端立即把当前审计视图标记“等待服务端重新核验”；后台依旧通过版本校验禁止旧结果被当成当前结果。

### 10.1 轮询与错误处理

- 发 POST /v1/drafts/{id}/audits 返回 202 后，以适度退避轮询 GET /v1/audits/{id}；支持离开页面、重新打开继续查询。不采用含个人资料的 SSE/URL。
- 网络断开保留本地尚未提交的 UI 表单，但不把敏感内容永久缓存；重试创建使用 Idempotency-Key，防止双重审计。
- 409 VERSION_CONFLICT：展示服务器 revision 与当前未提交的修改，用户选择继续编辑/重新加载。绝不自动覆盖草表。
- 422 INVALID_ADMISSION_UNIT：定位相应代码并保持前导零；503 SOURCE_NOT_READY：明确仅可历史练习；429：说明稍后重试，不宣称计算成功。
- 401/403/404：离开受限内容后清空对应 Query cache；无权访问时不显示草表名称或推断其他家庭存在。
- model explanation 失败：显示**模板解释**，仍可浏览机器规则检查和官方来源。
- 空态必须区分“还没有草表”“没有可比历史数据”“规则未覆盖”“检查未完成”，不能统一写“暂无风险”。

## 11. 无障碍、移动端与可信视觉语言

目标 WCAG 2.2 AA（待实际审计），重点：
- 360px 手机到 1440px 桌面，主要按钮/行高适合触控，中文文本在 200% 缩放不截断；
- 错误与风险状态文本和 icon 双编码，不仅颜色；屏幕阅读器可朗读“未核实原因、来源链接、下一步”；
- 志愿排序操作可全键盘完成，焦点移动有语义通知，表格列标题关联，不把拖拽作为唯一方式；
- 审计异步完成只在合理时用 aria-live 提醒，不频繁播放全部结果；
- 任何模型文本使用安全 Markdown renderer（无任意 HTML）与内容白名单；不把来源正文拼成 JSX/innerHTML；
- 真实来源缺失时留灰色“尚未核实”提示，不使用看似权威的徽章或“官方认证”标识；
- 重视容易被忽略的学生阅读负荷：关键硬约束始终在最上方，专业术语可展开，解释保留短版和详细版。

## 12. 可用性实验与交互验收（建议标准，未测试）

| 测试任务 | 受试者操作 | 成功条件 |
